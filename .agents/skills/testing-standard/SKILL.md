# 项目测试规范

## 测试位置与工具

- 单元测试放在 `test/unit`，按源码模块路径组织。
- 端到端测试放在 `test/e2e`，使用 Supertest 验证真实 HTTP 行为。
- 测试框架统一使用 Vitest；禁止引入 Jest、Mocha 或其他测试框架 API。
- 测试初始化统一使用 `test/setup.ts`，不得在单个测试文件重复初始化全局环境。

## 测试设计

- 先明确被测公开行为、输入、输出和失败边界，再编写测试。
- 优先验证业务行为和接口契约，不依赖私有方法、调用顺序或内部实现细节。
- 测试数据必须自包含，禁止依赖测试执行顺序、共享可变状态或真实外部服务。
- 不要通过断言列表第一项、最后一项等隐含排序来定位业务记录；使用稳定的业务标识查询，例如权限编码、资源 ID 或唯一名称。
- 外部服务、时间、随机值和持久化依赖应通过明确的接口或 mock 隔离。
- 测试不可变性：调用被测逻辑后，除明确约定的状态变化外，输入对象和无关记录不得被修改。

## 必测场景

新增或修改业务功能至少覆盖：

- 正常流程；
- 参数校验和空输入；
- 未认证、无权限和越权访问；
- 资源不存在、重复数据和边界值；
- 外部依赖失败及错误传播；
- 批量处理中的全成功、部分失败和全部失败；
- 数据持久化失败后的补偿或一致性行为。

涉及权限和数据范围时，必须分别验证本人数据、他人数据、全量权限和权限缺失四类情况。

## Mock 与断言

- mock 只替代测试边界外的依赖，不 mock 被测业务自身。
- 每个测试独立创建依赖和数据，测试结束后恢复 spies、fake timers 和全局 mock。
- 错误断言同时验证异常类型或 HTTP 状态码，以及稳定的业务错误信息。
- 对集合断言使用业务键匹配，不把实现排序当作契约；只有排序本身是需求时才断言顺序。
- 避免过宽的 `toBeTruthy`、`toEqual(expect.anything())` 和无意义的调用次数断言。

## 验证流程

修改测试或生产代码后按顺序执行：

1. 运行目标测试文件，确认快速反馈。
2. 运行相关模块测试。
3. 执行 `pnpm typecheck`。
4. 执行 `pnpm lint`，审查警告而不是默认忽略。
5. 执行完整 `pnpm test`；涉及接口时执行 `pnpm test:e2e`。
6. 涉及构建或模块装配时执行 `pnpm build`。

测试失败时先判断是测试假设、隔离、mock 或生产逻辑问题，不得为了通过测试给生产代码增加与业务无关的排序、特殊分支或硬编码。
