# TypeScript 编码风格规范

## 不可变性

优先创建新对象，不直接修改传入对象、配置对象或共享状态：

```typescript
return { ...value, ...changes };
```

确需修改时，应限定在明确的局部生命周期内，并保证不会改变调用方持有的对象。

## 注释与命名

- 公共类、函数、方法、接口、类型、DTO、Entity 和配置属性使用中文 JSDoc，说明当前行为和边界。
- 参数和返回值在行为不明显或存在约束时使用 `@param`、`@returns` 和 `@throws`。
- 注释解释代码当前做什么，不记录修改过程、历史原因或未实现功能。
- 名称使用准确的领域或基础设施含义，避免无法表达职责的泛化名称。
- 文件名使用 kebab-case，类型和类名使用 PascalCase，函数和变量使用 camelCase。

## 控制流与分支

- 对已经确定结果的分支使用提前返回（Guard Clause），在分支内完成该路径的副作用和结果处理后立即结束函数。
- 让主流程保持在较低嵌套层级，避免通过布尔变量贯穿多个互斥分支。
- 当不同分支具有不同的副作用、返回结果或错误处理时，使用独立代码块，不使用复杂条件表达式合并流程。
- 三元表达式仅用于简单、无副作用的值选择；涉及多步操作、日志、响应或异常处理时使用 `if` 分支。
- 优先保证控制流的语义边界清晰，再考虑压缩代码行数。

## 业务语义命名

- 方法名必须表达实际副作用和生命周期语义；避免使用无法区分创建、更新、软删除、恢复和物理删除的泛化动词。
- `find` 表示可返回空值的查询，`get` 表示预期存在的查询，`create`、`update`、`softDelete`、`restore` 和 `hardDelete` 只在对应语义成立时使用。
- 领域错误、应用错误、持久化错误和协议错误使用可区分的类型或命名，禁止在底层通过模糊异常名称传递跨层语义。

## 类型与接口

- 开启并遵守 TypeScript strict 模式。
- 优先使用明确的接口、联合类型和类型守卫，不使用无约束的 `any` 隐藏边界错误。
- 配置、API 响应、错误响应和外部输入使用专用类型；不要把 `process.env` 或原始请求对象直接传播到业务层。
- 类型声明应反映可空性和可选性；不要用非空断言掩盖实际可能为空的运行时值。
- 可复用的已导出类型使用具名声明，不在方法签名上重复书写相同的内联对象类型。
- 类型声明与实现分离：类型放在所属 `types/` 目录，函数放在所属 `utils/` 目录，由实现文件导入类型。
- TypeORM 运行时填充的 Entity 属性按 Entity 规范使用 `!`；其他类型只有在初始化事实明确时才使用非空断言。

## 导入与导出

- 项目使用 NodeNext ESM；本地 TypeScript 模块导入保留编译后的 `.js` 后缀。
- 当前源码使用相对路径；未来启用并完成工具链一致配置后，可使用 `@/*` 别名进行跨模块导入。
- `index.ts` 作为公共桶文件时优先使用 `export *`；发生命名冲突、需要隐藏内部实现或存在循环依赖风险时使用显式导出。
- 避免跨领域模块导入内部文件；通过公开导出和 Service/接口协作。

## 工具函数

- 领域纯函数放在所属模块的 `utils/<功能>.util.ts`，跨领域纯函数放在 `src/common/utils/<功能>.util.ts`，均使用命名导出。
- 当前公共工具能力包括 YAML 配置读取和合并、对象和日期处理、记录类型守卫、游标编解码、分页结果构造、密码规则校验、注册表校验错误构造和 MySQL 唯一键识别；新增工具前先检查 `src/common/utils/` 是否已有可复用实现。
- 相同职责的纯函数只保留一份实现，需要区分领域时通过参数传入领域标识，不在多个模块复制同一函数。
- 工具函数不得隐式读取环境、修改全局状态或吞掉错误；外部依赖通过参数或明确的服务接口传入。
- 不为尚未确认的业务创建通用工具、伪造 URL 转换器或领域专用 helper。

## 复杂度与文件边界

| 项目 | 约束 |
|---|---:|
| 函数行数 | 少于 50 行 |
| 文件行数 | 少于 800 行 |
| 嵌套层级 | 少于 4 层 |

接近限制时按职责拆分小函数或模块，不继续堆叠条件分支。

## 错误处理

- 不静默吞掉错误；必须显式处理、记录必要上下文后抛出，或交由全局异常机制处理。
- 配置和外部输入在系统边界快速失败，并返回可定位但不泄露敏感信息的错误。
- 不在底层工具函数中擅自转换业务错误；保持错误语义交由对应层处理。
- 异步流程必须正确等待并传播异常。

## 测试代码

- 单元测试放在 `test/unit`，端到端测试放在 `test/e2e`，测试初始化使用 `test/setup.ts`。
- 测试框架使用 Vitest，HTTP 场景使用 Supertest；不要引入其他测试框架的 API 或配置。
- 测试验证公开行为、边界条件、错误响应和不可变性，不只验证实现细节或注释文本。

## 规范来源与执行前检查

- 开始编码前先读取项目根目录 `AGENTS.md`、本目录 `.agents/skills/` 下全部相关 Skill、`package.json`、`tsconfig.json`、`.prettierrc`、`.oxlintrc.*` 及现有脚本；不得仅凭通用 TypeScript 经验推断项目规则。
- 以项目实际配置和命令为准。若 Skill 文档与 `package.json`、OXC 配置或源码行为不一致，先修正文档或明确冲突，不得跳过验证。
- OXC/Oxlint 是本项目实际 Lint 工具；Prettier 只负责格式化，不能代替 OXC 规则检查。
- 修改导入、类型、异步调用或文件结构后，必须重新检查对应文件的 OXC 规则，而不是只观察格式化结果。
- `AGENTS.md`、`SKILL.md` 等 Markdown 规范文件通常不在 TypeScript 的 Prettier、OXC 或 TypeScript 检查脚本范围内；修改它们时仍须人工检查标题层级、列表、代码块、空行和 UTF-8 编码，不能把未被工具扫描误认为格式正确。

## 格式化与 OXC Lint 验证

代码修改完成后，不能只运行 Prettier。必须同时执行项目实际配置的格式化、格式检查、OXC/Oxlint Lint 和 TypeScript 类型检查。

### TypeScript 项目验证顺序

1. 执行 `pnpm format`，或项目定义的等价格式化命令。
2. 执行 `pnpm format:check`，确认全部 TypeScript 文件符合 Prettier 规范。
3. 执行 `pnpm lint`，确认 `.oxlintrc.*` 中启用的规则全部通过。
4. 执行 `pnpm typecheck`，或等价的 `tsc --noEmit`。
5. 只有格式检查、Lint 和类型检查全部通过，才能报告编码规范验证通过；Lint 警告也必须审查，不能默认忽略。

### OXC/Oxlint 重点规则

- `import/newline-after-import`：最后一个 import 与业务代码之间保留一个空行；若存在多个连续 import，不在 import 组内部插入空行，只有 import 组结束后保留一个空行。
- `typescript/consistent-type-imports`：仅用于类型的导入必须使用 `import type`。
- 删除未使用的导入、变量和类型。
- 异步调用必须正确等待并传播异常，不能留下未处理 Promise。
- 不得通过关闭规则、降低规则级别或添加无依据的忽略注释规避问题。

### 失败处理

发现格式或 Lint 问题时，先修复新增或修改的文件，再重新执行完整验证。若自动格式化修改大量无关文件，应撤销无关变更，仅保留当前需求相关修改。
